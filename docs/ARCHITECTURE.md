## 🧩 Tanggung Jawab Tiap Layer

| Layer | Tanggung Jawab | Contoh |
|---|---|---|
| **models** | Konversi JSON API ⇄ object Dart, validasi tipe data | `User.fromJson()`, `Complaint.toJson()` |
| **services** | Komunikasi HTTP (Dio) ke backend Laravel, simpan token/cache lokal | `AuthService.login()` |
| **providers** | State aplikasi yang didengarkan widget (`ChangeNotifier`), orkestrasi loading/error | `AuthProvider.login()` memanggil `AuthService` lalu `notifyListeners()` |
| **screens** | Halaman UI, terhubung ke provider lewat `Provider.of` / `context.watch` | `LoginScreen` memanggil `authProvider.login(...)` |
| **widgets** | Komponen visual kecil yang dipakai ulang lintas screen | `AdminStatusBadge`, `SkeletonLoader` |
| **routes** | Definisi path, transisi halaman, dan guard berdasarkan status login/role | `AppRouter.createRouter()` |
| **theme** | Warna, tipografi, dan style komponen terpusat | `AppTheme.light` |

## 🔄 Alur Data (Data Flow)

Pola standar di seluruh app — UI tidak pernah memanggil Dio langsung, selalu lewat Provider → Service:

```
┌──────────┐     panggil method      ┌──────────────┐     HTTP request (Dio)     ┌──────────────────┐
│  Screen  │ ───────────────────────▶│   Provider    │ ──────────────────────────▶│  Backend Laravel  │
│ (Widget) │                          │(ChangeNotifier)│                            │   (REST API)      │
└──────────┘                          └──────────────┘                            └──────────────────┘
     ▲                                       │  ▲                                          │
     │      notifyListeners() → rebuild      │  │           Service (Dio + parsing)        │
     └───────────────────────────────────────┘  └──────────────────────────────────────────┘
                                                  AuthService / ComplaintService / dst.
```

1. **Screen** memanggil method di **Provider** (mis. `complaintProvider.fetchComplaints()`).
2. **Provider** set `isLoading = true`, `notifyListeners()`, lalu memanggil **Service**.
3. **Service** melakukan request via `Dio`, mengambil token dari `flutter_secure_storage`, lalu parsing response JSON ke **Model**.
4. **Provider** menerima hasil/​error, update state, `notifyListeners()` lagi.
5. **Screen** yang `watch`/`listen` provider otomatis rebuild.

Provider didaftarkan secara global di [`main.dart`](../lib/main.dart) lewat `MultiProvider`, sebagian besar dengan `lazy: true` agar baru dibuat saat pertama dipakai (menghindari request API yang tidak perlu saat splash).

## 🔐 Alur Autentikasi & Routing Guard

```
Splash (cek token di secure storage)
   │
   ├─ token valid ──► role == admin? ──► /admin   (AdminDashboardScreen)
   │                          └─ tidak ─► /home    (HomeScreen, bottom nav)
   │
   └─ tidak ada token ──► /landing ──► /login atau /register
```

## 🔔 Alur Push Notification (FCM)

1. `main.dart` menginisialisasi `FCMService` ~500ms setelah app start (menunggu provider siap) dan mendaftarkan `firebaseMessagingBackgroundHandler` untuk pesan saat app di background/terminated.
2. `FCMService.initialize()` minta permission notifikasi, membuat **Android notification channel** (`high_importance_channel`), dan setup `flutter_local_notifications` untuk menampilkan notifikasi saat app foreground (FCM auto-display dimatikan, supaya tampilan custom konsisten).
3. Setelah `AuthProvider` berubah ke `isAuthenticated`, `FCMService.reRegisterToken()` dipanggil untuk mendaftarkan token FCM ke backend, lalu `checkUnreadAndNotify()` mengecek notifikasi yang belum dibaca.
4. Tap notifikasi → `_onNotificationTapped` menavigasi via `navigatorKey` global (tanpa butuh `BuildContext` dari widget tree) ke halaman terkait (detail pengaduan, pengumuman, dll).
